# Hardening Plan

### A. Goal
Make VaultProxy safe to run in production AND very simple to use. Simplicity is a hard requirement.

### B. Simplicity rules
S1 A new user gets a working protected proxy in 3 steps: install, run, change base_url. No config file required.
S2 Convention over configuration. The total number of NEW settings in the whole hardening effort is at most 8; 3 are used so far (VAULT_PROFILE, MASK_SCOPE, NON_TEXT_POLICY), so at most 5 more. Each new setting needs a one-line justification. Existing settings keep names and defaults.
S3 No new abstractions: no plugin systems, store interfaces, dependency injection or user-supplied regex engine.
S4 No new runtime dependencies unless essential; optional features go in extras.
S5 Errors say what happened, why and how to fix it. No stack traces to clients, and never input text in an error.
S6 Delete before you add. Report net lines per phase and justify any phase over 400 added lines.
S7 Two profiles only: development (current behaviour) and production (refuses unsafe configuration).
If a requirement would make the tool harder to use, STOP and ask me a short question.

### C. Core contract (must stay true)
C1 Typed tokens [TYPE_N]; the same value gets the same token within a request; the vault is per-request, in memory only, never persisted.
C2 Fail closed: an unexpected masking error returns 503 and forwards nothing; STRICT_MODE plus an SLM failure returns 503.
C3 X-Vault-Report keeps its fields (additive changes only; counts only, never values).
C4 Streaming restore never leaks partial tokens (split-at-every-position tests keep passing).
C5 Everything works with GEMMA_BACKEND=off and offline.
C6 Existing env var names and development-profile defaults are unchanged.
C7 Existing tests pass, except tests that froze a "KNOWN LEAK" and are deliberately updated (list each by name).

### D. Honesty rules
Docs, UI and README must be true and measured. Never write "guarantees", "zero-trust", "100% safe", "ensures compliance"; say it reduces risk. Compliance notes: supports safeguards, not legal advice. Compare with other tools only using facts verified from their official docs in this session. Never print or log raw prompts, replies, detected values or secrets. Fake data only. Never push to a remote.

### E. Report format (end of every phase)
(1) What a user can now do, in 3 lines. (2) Commands for me to try it, including real proxy runs, not only filtered pytest. (3) Tests and the real coverage table (run pytest --cov=vaultproxy --cov-report=term-missing without disabling addopts). (4) Regression report: golden tests unchanged yes/no, and each deliberately changed test with a reason. (5) Net lines of code, and any new settings with justification. (6) Risks. Then update docs/PROGRESS.md, commit, and STOP and wait for "next".

### F. Remaining plan
PHASE 2.5 (do this now): fix and prove Phase 2, no new features.
 1. Explain how the structural allowlist is applied. Change it so EVERY string value is scanned, except the top-level "model" value and the "role" and content-part "type" values at their exact structural positions. Never skip keys inside tool arguments, metadata, user, tool schemas or user-supplied objects. Tests: a fake PAN and fake Aadhaar placed in metadata.id, metadata.type, metadata.mode, the user field, and tool arguments with keys id, type, object, mode, role; none may reach the upstream.
 2. Show how the SLM layer is called in deep scope. It must be ONE call per request over the combined text, with an internal size cap and a skip for strings under 4 characters, strings with no letters, and base64 or hex-looking strings. Test: 40 string fields plus a 20,000-character tools list produce exactly one SLM call within the timeouts. Define and test what happens when the cap is exceeded (strict: 503; non-strict: rules only with degraded=true).
 3. Streaming: key restorers by (choice index, tool_call index, field). Tests: two parallel tool calls with tokens split across fragments; mid-stream upstream error; upstream closing early; client disconnect (upstream request cancelled, buffers dropped, no leaked tasks or connections). Flush buffers on every exit path.
 4. Contract tests with the official OpenAI Python SDK against the proxy with an in-process mock upstream: normal, streaming, tools (stream and non-stream), JSON mode, n=2. Include a restored value containing a double quote, a backslash and a newline; the JSON must stay valid and the value must be escaped exactly once.
 5. Embeddings: add header X-Vault-Warning saying embeddings of masked text are not comparable across requests, plus a short docs note. Input given as token-id lists cannot be inspected: in production return 400 with a clear message.
 6. Rename the PROFILE setting to VAULT_PROFILE everywhere (no alias).
 7. Confirm the updated KNOWN LEAK test sets MASK_SCOPE=deep explicitly, and add a test proving a default development request behaves as before Phase 2.
 8. Evaluate only (do not apply): if deep were the default in every profile, would all golden tests pass? Report the result and the lines that could be deleted by removing "messages" mode.
 9. Show the real coverage table, ruff --statistics, mypy, and line counts per file. If vaultproxy/server.py is over 300 lines, move the deep-walk code into vaultproxy/masking.py.
PHASE 3 Easy to use: CLI "vaultproxy" with run (--upstream, --port, --host default 127.0.0.1, --strict; works rules-only without an SLM), init (write a commented .env, never overwrite; in production generate a random auth token), doctor (plain-English PASS/WARN/FAIL with a fix hint: Python version, port, upstream reachable, API key present but never printed, Ollama reachable, configured model installed, tiny SLM test call, production-profile problems), check (dry run on text or --file: entity types found plus masked text, no upstream call), version. A startup banner (version, profile, protection level "rules only" or "rules + <model>", strict on/off, bind address, loud warning if bound beyond localhost). Library API with just mask(text) and restore(text, vault) plus a 6-line README example. Production profile refuses to start and prints ALL problems at once with fixes (missing auth token, demo mode on, upstream not https unless localhost, strict mode off without explicit override, heuristic fallback enabled). Docs split into Essentials (UPSTREAM_BASE_URL, UPSTREAM_API_KEY, VAULT_AUTH_TOKEN, STRICT_MODE, GEMMA_BACKEND, GEMMA_MODEL) and Advanced. OpenAI-style JSON errors with request id and hint; validation errors never echo input.
PHASE 4 Better detection, kept small: add single-file detectors with valid/invalid test vectors, a score and a docs entry: card (Luhn), GSTIN (verify the check character against an authoritative spec or mark heuristic), voter ID, Indian passport, vehicle registration, IPv4/IPv6, database URLs with credentials, private key blocks, more API key formats, password=/secret= assignments. Bank account, date of birth and PIN code only with nearby context keywords (low score). Unverifiable format rules are marked heuristic; never invent a checksum. Allow/deny lists as two plain-text files found through ONE setting (VAULT_LISTS_DIR). Cap input length per detector, add backtracking-safety tests with time checks, use general Unicode decimal-digit normalisation (one character in, one out). Property-based tests (hypothesis) for the tokenizer and restorer only. Update the benchmark per entity, with generated and held-out results reported separately.
PHASE 5 Production safety basics: VAULT_AUTH_TOKEN (constant-time compare, required in production). Safe built-in limits (max body size, max request time, max concurrent requests with 429 and Retry-After), at most one documented setting each. One JSON log line per request with request_id, status, milliseconds, counts by entity type, degraded, strict; never content. /healthz and /readyz; optional /metrics only with the [metrics] extra (5 metrics, no values in labels). CORS off; demo endpoints 404 unless DEMO_MODE=true; heuristic fallback disabled in production; graceful shutdown; one shared httpx client with explicit timeouts and TLS verification always on. Security tests: auth bypass, oversize bodies, invalid UTF-8, header injection, deeply nested JSON. Write SECURITY.md and a one-page docs/THREAT_MODEL.md (what is protected, and what is not: context stays, missed detections, prompt injection, compromised host, provider-side logging of masked text).
PHASE 6 Packaging and deployment: pyproject console entry point and a [metrics] extra; verify pip install . in a clean virtual environment. Dockerfile (slim, non-root, healthcheck), docker-compose.yml (proxy + Ollama, with a one-line model pull instruction), a systemd unit example, and ONE Kubernetes example (Deployment, Service, NetworkPolicy) under docs/examples. No Helm. Verify end to end with the mock upstream, in a clean environment and in Docker.
PHASE 7 Documentation (short, plain Markdown): README (what and why in 5 lines, the 3-step quickstart, copy-paste snippets for OpenAI Python, OpenAI Node, curl and LangChain, what it protects and does not, how to see it working, a verified-facts comparison, limits). docs/: HOW_IT_WORKS.md with a diagram, CONFIG.md, PRODUCTION.md (one-page checklist: sidecar versus shared internal gateway, bind address, auth, TLS through a reverse proxy with response buffering off for SSE, strict mode, keeping Ollama off public networks, what to monitor, upgrade and rollback), DETECTORS.md, TROUBLESHOOTING.md (top 10 problems), CONTRIBUTING.md. No docs-site generator.
PHASE 8 CI and release: GitHub Actions for lint, mypy on core modules, tests with coverage, golden tests, smoke test, build, pip-audit, secret scan and Docker build; a release workflow to PyPI and GHCR with semantic versioning and a CHANGELOG check; Dependabot; actions pinned by commit SHA.
PHASE 9 Final check: console works offline with all assets local, shows the exact model name and honest source badges. Add scripts/live_gemma_check.sh that exercises real Ollama with the configured Gemma model and prints PASS/FAIL for: model present, one masked request, strict mode with the SLM stopped, recovery after restart. Run doctor and the 3-step quickstart in a clean environment and report the real time it takes. One load-test script; publish measured numbers with hardware noted (protection off, rules only, rules plus SLM). Re-run the claims audit so every claim is true or removed. Tag v1.0.0-rc1 and write release notes with known limitations.

### G. Not now (do not build)
Signed receipts, audit hash chain, policy YAML, reply scan, Postgres or Mongo stores, Helm, OpenTelemetry, per-token rate limits, user-supplied regex detectors, native provider adapters, image redaction, a docs-site generator.
